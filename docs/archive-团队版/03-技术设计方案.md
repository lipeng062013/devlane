# DevLane 技术设计方案

| 项 | 内容 |
| --- | --- |
| 版本 | v1.0 |
| 日期 | 2026-10-27 |
| 依赖文档 | `01-需求分析.md`、`02-PRD.md` |

## 1. 设计原则

1. **事件流是唯一事实来源**。会话视图、泳道图、统计、Jira 回写都是事件流的投影。
2. **隔离优先于便利**。每条 lane 有独立 worktree、独立沙箱、独立凭据。
3. **人是流程节点**。门禁是事件，进入状态机，可审计。
4. **外部输入不可信**。Jira 正文、仓库内容、工具输出都按数据处理，权限由 lane 策略决定。
5. **先单机跑通，再拆服务**。MVP 用模块化单体，边界按未来拆分线划好。

## 3. 技术选型

| 层 | 选型 | 理由 |
| --- | --- | --- |
| 前端 | React + TypeScript + Vite，状态用 Zustand，泳道图用 SVG（节点超 3000 时切 Canvas） | 泳道图是自绘拓扑，SVG 便于交互和无障碍 |
| 后端 | Node.js + TypeScript（Fastify） | 与前端共享事件类型定义；SSE 支持成熟 |
| 数据库 | PostgreSQL 16 | 事件表按 lane 分区；JSONB 存 payload；`LISTEN/NOTIFY` 做轻量推送 |
| 队列与调度 | PostgreSQL 表 + `FOR UPDATE SKIP LOCKED` | MVP 不引入额外中间件 |
| 缓存 | Redis（可选，限流与 Jira 元数据缓存） | MVP 可退化为进程内缓存 |
| 对象存储 | MinIO / S3 | 产物、完整日志、截图 |
| 沙箱 | Docker（后续可换 Firecracker / gVisor） | 开发成本低，隔离满足 MVP |
| 模型接入 | 自建模型网关，统一 OpenAI 兼容接口 | 屏蔽厂商差异，集中计量和限流 |
| 部署 | docker-compose 起步，K8s 为后续路径 | 与团队现有运维能力匹配 |

## 4. 事件模型（核心）

### 4.1 事件结构

```ts
interface LaneEvent {
  id: string;               // ULID，按时间可排序
  laneId: string;
  runId: string | null;
  seq: number;              // lane 内单调递增，用于断线补拉
  parentIds: string[];      // 因果父事件，泳道图的边来自这里
  type: EventType;
  actor: { kind: 'agent' | 'human' | 'system'; id: string; model?: string };
  ts: string;               // ISO 8601
  payload: Record<string, unknown>;  // 按 type 校验的 JSON
  artifactIds: string[];
  prevHash: string;         // 同 lane 上一事件的哈希，形成哈希链
}
```

`seq` 在 lane 内由数据库序列保证。`(laneId, seq)` 唯一，写入冲突即重试。`prevHash` 使轨迹可校验是否被篡改。

### 4.2 事件类型

与图例的 15 类对应，并补充系统类事件：

| 类型 | 图例 | payload 关键字段 |
| --- | --- | --- |
| `commit` | 提交/保存 | sha、message、additions、deletions、files |
| `test_pass` / `test_fail` | 测试 ✓ / ✗ | command、exitCode、durationMs、summary、attempt |
| `artifact` | 产物 | artifactId、kind、title |
| `gate_open` / `gate_resolved` | 等待你 | gateId、gateType、decision、resolver |
| `handoff` | 交接 | fromActor、toActor、briefArtifactId |
| `review_pass` | 审查通过 | reviewer、notes |
| `tool_call` | 工具调用 | tool、args（脱敏）、exitCode、outputRef |
| `branch` | 分支 | name、baseSha |
| `merge` | 合并 | prNumber、mergeSha |
| `checkpoint` | 检查点 | sha、label |
| `model_switch` | 模型切换 | from、to、reason |
| `context_compact` | 上下文压缩 | tokensBefore、tokensAfter、summaryArtifactId |
| `error` | 错误 | code、message、retryable |
| `retry` | 重试 | attempt、reason |
| `cross_ref` | 跨线引用 | sourceLaneId、sourceEventId、artifactId |
| `brief_ack` | 交接确认 | briefArtifactId、nextStep |
| `jira_sync` | 回写 | operation、status、jiraRef |

### 4.3 写入规则

1. 所有写入走 `EventService.append()`，单事务内完成「校验 payload、计算 seq、计算哈希、写表」。
2. payload 先过 JSON Schema 校验，不合格拒绝并记 `error`。
3. 大体积内容（命令输出、diff）写对象存储，事件内只放引用和截断预览。
4. 事件表按 `laneId` 哈希分区，索引 `(laneId, seq)` 和 `(type, ts)`。
5. 写入成功后 `NOTIFY lane_events`，推送层按订阅转发。

### 4.4 投影

| 投影 | 来源 | 用途 |
| --- | --- | --- |
| 会话视图 | 单 lane 事件按 `seq` 顺序，按 `runId` 与连续 `tool_call` 分组成步骤组 | 中栏 |
| 泳道图 | 全部活跃 lane，节点取关键类型，边取 `parentIds` 与 `cross_ref` | 右栏 |
| lane 状态 | 对 `gate_*`、`error`、`merge` 等事件折叠 | 左栏与状态机 |
| 成本 | `tool_call`（模型调用）事件聚合 | 成本页 |
| Jira 回写任务 | 订阅特定事件产生待发送操作 | 连接器 |

投影可从零重放重建，所以修改投影逻辑不需要迁移数据。

## 5. Jira 连接器

### 5.1 认证

| 部署形态 | 方式 | 说明 |
| --- | --- | --- |
| Jira Cloud | OAuth 2.0 (3LO) | scope：`read:jira-work`、`write:jira-work`、`offline_access`；授权后调用 `accessible-resources` 取 `cloudId` |
| Data Center | 个人访问令牌（PAT） | `Authorization: Bearer <PAT>`，基地址为实例自身地址 |

Cloud 的 API 基地址是 `https://api.atlassian.com/ex/jira/{cloudId}/rest/api/3`。access token 过期前用 refresh token 轮换，新 refresh token 立即落库。token 用 AES-256-GCM 加密存储，密钥来自环境变量或密钥管理服务。

### 5.2 读取

| 目的 | 接口 | 要点 |
| --- | --- | --- |
| 列看板 | `GET /rest/agile/1.0/board` | 分页 |
| 列 Sprint | `GET /rest/agile/1.0/board/{id}/sprint?state=active` | 默认只拉 active 与 future |
| Sprint 内 issue | `GET /rest/agile/1.0/sprint/{id}/issue` | 指定 `fields` 减少体积 |
| JQL 检索 | `GET /rest/api/3/search/jql` | 使用 `nextPageToken` 翻页，请求里显式列出 `fields` |
| 批量取详情 | `POST /rest/api/3/issue/bulkfetch` | 一次取多条，减少请求数 |
| 字段元数据 | `GET /rest/api/3/field` | 用来解析自定义字段 ID |
| 变更历史 | `GET /rest/api/3/issue/{key}/changelog` | 同步时判断谁改了什么 |

Jira 描述和评论是 ADF（Atlassian Document Format）。入库保留原始 ADF，同时转成 Markdown 供 agent 使用。转换器遇到未知节点时保留纯文本并记警告，不丢内容。

### 5.3 字段映射

自定义字段 ID（如验收标准、故事点）在每个站点都不同。流程：

1. 首次绑定时调用 `/field`，按名称与类型匹配候选。
2. 在界面展示匹配结果，由管理员确认或手动指定。
3. 映射存入 `project_field_mapping`，后续导入只按映射取值。
4. 找不到验收标准字段时，尝试从描述里解析「验收标准 / Acceptance Criteria」标题下的列表。

### 5.4 同步

- **Webhook 优先**：订阅 `jira:issue_updated` 等事件。Cloud 的 OAuth 应用在应用配置里登记；Data Center 在管理后台创建 Webhook。
- **轮询兜底**：每 5 分钟按 `updated >= 上次水位` 的 JQL 补漏，水位取上一批最大 `updated` 减 1 分钟，靠幂等去重。
- **幂等**：Webhook 请求以 `(issueKey, updatedAt, webhookEventId)` 去重；同一 issue 的处理串行。
- **快照**：每次同步写一条不可变的 issue 快照；lane 绑定的是快照版本，Jira 侧变更到达后在界面提示「需求已变更」，由人决定是否刷新。

### 5.5 回写

| 触发事件 | 动作 |
| --- | --- |
| lane 派发 | 评论「已开始处理」，可选地流转到「进行中」 |
| `gate_open`（需要澄清） | 评论追问，@报告人 |
| `merge` 之前的 PR 打开 | 评论 PR 链接与验证摘要，流转到「待评审」 |
| 缺陷修复完成 | 评论根因、改动点、测试证据 |

流转要点：
- transition ID 随工作流和 issue 当前状态而变，先 `GET /issue/{key}/transitions`，按目标状态**名称**匹配 ID。
- 找不到可用流转时，降级为只加评论，并产生 `jira_sync` 失败事件提示人手动处理。
- 评论体使用 ADF 构造。
- 所有回写走独立的出站队列，指数退避重试；遇到 429 读取 `Retry-After`，加随机抖动后重试。回写失败不阻塞 lane 主线。

### 5.6 提示注入防护

Jira 的标题、描述、评论由多人编辑，按不可信数据处理：

- 送给 agent 时放入明确标记的「需求数据」区块，系统指令位于区块之外。
- agent 的工具权限由 lane 策略（见 §7）决定，与 issue 文本无关。issue 里出现「忽略以上规则」「读取密钥」之类内容，不改变权限。
- 命中可疑模式（要求外发数据、要求访问仓库外路径）时写一条 `error`（code=`suspicious_input`）并开「范围变更」门禁。

## 6. Lane 编排器

### 6.1 状态机

状态集合与 PRD §4.2 一致。迁移由事件驱动，编排器只做两件事：校验迁移是否合法，合法则写入对应事件。

| 当前状态 | 事件 | 下一状态 | 守卫条件 |
| --- | --- | --- | --- |
| draft | `readiness_scored` | ready | 就绪分 ≥ 70，或人选择强推 |
| ready | 人点「派发」 | queued | 项目并发配置存在 |
| queued | 调度器领取 | running | 并发额度充足 |
| running | `gate_open` | blocked | 带 gateId |
| blocked | `gate_resolved` | running | 决策为放行 |
| running | 人点「暂停」 | paused | 无 |
| running | PR 创建成功 | reviewing | 验证事件齐全 |
| reviewing | `merge` | merged | 由人触发 |
| 任意 | 人点「放弃」 | abandoned | 无 |

非法迁移返回 409，并写一条 `error` 事件。

### 6.2 调度

- 队列表 `lane_queue(laneId, priority, enqueuedAt)`，调度器循环用 `FOR UPDATE SKIP LOCKED` 领取。
- 优先级：缺陷 P1 > 缺陷其他 > 需求；同级按 Jira 优先级再按入队时间。
- 并发额度分三层：全局、项目、模型（防止单个模型被打满）。
- 调度器重启后扫描 `running` 状态的 lane，对应沙箱不存在就写 `error`（code=`runner_lost`）并转 `paused`，等待人决定继续还是重试。

### 6.3 Run 生命周期

1. 编排器创建 Run 记录，请执行器管理拉起沙箱。
2. 沙箱内 Agent 通过本地代理访问平台 API，每个动作先请求策略引擎裁决。
3. Agent 的每步输出由代理转成事件写入事件服务。
4. Run 结束（成功、失败、超时、被中断）后，执行器管理回收沙箱，保留 worktree。
5. 失败自动重试最多 3 次，每次写 `retry` 事件，尝试序号递增；超出后开门禁。

### 6.4 缺陷流水线守卫

缺陷类 lane 的阶段由编排器强制：

```text
reproduce → red_test → locate → fix → green → regression_check → pr
```

- `red_test` 阶段结束的条件：存在一条 `test_fail` 事件，其 `command` 命中项目声明的测试命令，且关联的测试文件在本 lane 新增或修改。
- 未满足时，策略引擎拒绝 `fix` 阶段的写文件操作（只允许写测试目录）。
- `green` 阶段要求同一条命令出现 `test_pass`，并且受影响模块测试集通过。

## 7. 沙箱与策略引擎

### 7.1 沙箱规格

| 项 | 默认值 |
| --- | --- |
| 镜像 | 项目声明的基础镜像，平台注入 agent 运行时 |
| 用户 | 非 root，UID 固定 |
| 挂载 | 仅 lane 的 worktree（读写）、只读工具缓存 |
| 资源 | 2 CPU、4 GB 内存、10 GB 磁盘，单 Run 45 分钟 |
| 网络 | 默认拒绝出站；白名单含包仓库镜像、模型网关、Git 远端（只读 fetch）、Jira |
| 凭据 | 短期令牌，Run 开始时注入，结束销毁；不挂载宿主机 SSH 目录 |

### 7.2 策略引擎

每个工具调用先过策略引擎，输出 `allow / deny / gate`。

| 规则类别 | 示例 | 结果 |
| --- | --- | --- |
| 路径 | 写 worktree 之外的路径 | deny |
| 命令 | `git push --force`、`rm -rf /`、修改 git remote | deny |
| 范围 | 修改 lane 声明范围外的文件 | gate（范围变更） |
| 高风险文件 | 依赖锁文件、数据库迁移、鉴权、支付目录 | gate（高风险操作） |
| 网络 | 访问白名单之外的域名 | deny |
| 阶段 | 缺陷 lane 在 `red_test` 前写业务代码 | deny |

规则放在项目配置里，版本化管理。每次裁决都写入 `tool_call` 事件的 `policy` 字段，便于事后核对。

## 8. 交接与上下文管理

### 8.1 Brief 生成

交接触发时，编排器调用一个独立的「简报生成」步骤，输入为事件流投影，输出为符合 PRD §4.6 schema 的 JSON 和一份 Markdown 渲染版，均存为产物。

1. `done`、`artifacts`、`repo_state` 由事件和 git 状态直接计算，不经过模型，避免遗漏或编造。
2. `goal`、`acceptance` 取自 issue 快照。
3. `plan`、`decisions`、`todo`、`open_questions`、`next_step` 由模型根据最近事件摘要，生成后经 schema 校验。
4. 缺字段时拒绝交接，并写 `error` 事件。

### 8.2 交接校验

- 新执行者启动时只加载 Brief、issue 快照、`repo_state` 对应的代码，不加载旧会话全文。
- 首个事件必须是 `brief_ack`。
- 退化检测：前 3 个事件的工具调用与 Brief 的 `done` 条目重复度高于阈值时，写 `handoff_degraded` 标记，并在泳道图节点上显示警示。

### 8.3 上下文压缩

- Run 内 token 使用量达到模型窗口的 75% 时触发。
- 压缩产出摘要产物，写 `context_compact` 事件，记录前后 token 数。
- 原始事件不删除，压缩只影响送入模型的上下文。

## 9. 前端设计

### 9.1 页面结构

| 页面 | 内容 |
| --- | --- |
| 看板导入 | 选站点、看板、Sprint；issue 列表带就绪分；批量创建 lane |
| 工作台 | 左栏 lane 列表，中栏会话视图，右栏泳道视图，底部输入区 |
| 门禁中心 | 所有待处理门禁，按紧急度排序 |
| 成本页 | 按 lane、模型、日期的聚合 |
| 项目设置 | Jira 绑定、字段映射、策略规则、测试命令、流水线模板 |

### 9.2 实时数据

- 前端对当前打开的 lane 订阅 `GET /lanes/{id}/events/stream`（SSE），请求头带 `Last-Event-ID`（即 `seq`）。
- 断线重连后服务端从该 `seq` 之后补发，前端按 `seq` 去重。
- 泳道图订阅 `GET /projects/{id}/events/stream`，服务端只推送关键类型事件，减少流量。

### 9.3 泳道图渲染

- 布局：横向每 lane 一列，纵向按事件时间对齐；同一时刻的并发事件在各自列内对齐到同一行。
- 节点用 SVG，超过 3000 节点切换 Canvas 并保留命中检测。
- 边由 `parentIds` 生成，`cross_ref` 画为弧线，点击高亮源与目标。
- 点击节点后，中栏滚动到对应 `seq`，反向同理，两者共享同一个选中事件状态。
- 筛选项：仅阻塞、仅失败、仅需要我。

### 9.4 会话视图分组

分组规则在前端纯函数中实现，可单测：

1. 同一 `runId` 内，连续的 `tool_call` 合并为一个步骤组。
2. 步骤组标题取组内最后一个 `commit` 或 `artifact` 的摘要，没有则取首个工具名。
3. 组头显示步数和累计耗时。
4. `error` 与 `test_fail` 所在组默认展开，其余默认折叠。

## 10. 数据模型

```sql
CREATE TABLE project (
  id uuid PRIMARY KEY, name text, repo_url text, default_branch text,
  jira_site_id uuid, jira_project_keys text[], policy jsonb, created_at timestamptz
);
CREATE TABLE jira_site (
  id uuid PRIMARY KEY, kind text,            -- 'cloud' | 'datacenter'
  base_url text, cloud_id text,
  token_enc bytea, refresh_token_enc bytea, token_expires_at timestamptz
);
CREATE TABLE project_field_mapping (
  project_id uuid, logical_name text,        -- 'acceptance','story_points',...
  jira_field_id text, PRIMARY KEY (project_id, logical_name)
);
CREATE TABLE issue_snapshot (
  id uuid PRIMARY KEY, project_id uuid, issue_key text, version int,
  raw_adf jsonb, markdown text, fields jsonb, readiness_score int,
  jira_updated_at timestamptz, UNIQUE (project_id, issue_key, version)
);
CREATE TABLE lane (
  id uuid PRIMARY KEY, project_id uuid, issue_snapshot_id uuid,
  state text, branch text, worktree_path text, executor text,
  budget_cents int, created_at timestamptz
);
CREATE TABLE run (
  id uuid PRIMARY KEY, lane_id uuid, model text, attempt int,
  started_at timestamptz, ended_at timestamptz, tokens_in bigint, tokens_out bigint
);
CREATE TABLE lane_event (
  id text, lane_id uuid, run_id uuid, seq bigint,
  type text, actor jsonb, ts timestamptz, payload jsonb,
  parent_ids text[], artifact_ids uuid[], prev_hash text,
  PRIMARY KEY (lane_id, seq)
) PARTITION BY HASH (lane_id);
CREATE TABLE artifact (
  id uuid PRIMARY KEY, lane_id uuid, kind text, storage_key text,
  sha256 text, size bigint, created_by_event text
);
CREATE TABLE gate (
  id uuid PRIMARY KEY, lane_id uuid, type text, status text,
  assignee text, opened_at timestamptz, due_at timestamptz,
  decision text, resolved_by text, resolved_at timestamptz
);
CREATE TABLE jira_outbox (
  id uuid PRIMARY KEY, lane_id uuid, operation jsonb, status text,
  attempts int, next_attempt_at timestamptz, last_error text
);
```

要点：`lane_event` 禁止 UPDATE 和 DELETE，通过数据库角色权限与触发器双重限制。`jira_outbox` 保证回写至少一次，对接口调用附带幂等键（评论内容中带事件 ID 标记，重试前先查重）。

## 12. 安全设计

| 面 | 措施 |
| --- | --- |
| 凭据 | Jira token、仓库凭据 AES-256-GCM 加密存储；日志与事件 payload 写入前脱敏（token、Authorization、密钥格式字符串） |
| 身份 | 平台登录走公司 SSO（OIDC）；角色分管理员、开发、只读 |
| 沙箱 | 非 root、网络白名单、资源上限、单 Run 短期凭据 |
| 提示注入 | Jira 与仓库内容按数据处理，权限只由策略引擎决定（见 §5.6、§7.2） |
| Webhook | 校验共享密钥或签名，拒绝重放（时间戳 + 事件 ID 去重） |
| 审计 | 事件哈希链；门禁放行记录操作人；事件表不可更新、不可删除 |
| 数据保留 | 轨迹与产物默认保留 90 天，可按 lane 导出与删除（删除走独立的管理员流程并记审计日志） |
| 主干保护 | 平台不持有合并主干的权限，只能推 `devlane/*` 分支并开 PR |

## 13. 部署与运维

MVP 用 docker-compose：`web`、`api`、`scheduler`、`runner-manager`、`postgres`、`minio`、`model-gateway`。

- `runner-manager` 需要访问 Docker 套接字，单独部署在专用主机，不与业务服务同机。
- 数据库每日全量备份，WAL 归档；对象存储开启版本控制。
- 指标：lane 状态分布、队列深度、门禁滞留、Run 失败率、Jira 出站队列积压、模型延迟与 token。
- 告警：出站队列积压超过 100 条、`runner_lost` 连续出现、模型网关错误率超过 5%。
- 配置通过环境变量注入，密钥放密钥管理服务。
