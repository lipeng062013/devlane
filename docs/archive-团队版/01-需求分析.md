# DevLane 需求分析

> 代号 DevLane（工作名，取「泳道 / 任务线」之意）。本文只回答一个问题：为什么值得做、做成什么样才算对。

## 一、参考图拆解

截图是一个三栏工作台，加上顶部一条控制带。把每个区域「意味着什么」拆出来，能直接得到产品的骨架。

### 左栏：任务线列表

- 按项目分组（视频学习、外网调研、Lancer、小红书），组内每条任务带运行计数（`2/5`、`2/4`）和状态色点，任务下面一行是 worktree 路径（`wt/douyin-dl`）。
- 推断：**一条任务 = 一条独立工作线 = 一个独立 git worktree**。计数表示这条任务名下挂了几个并行会话，`2/5` 是「5 条线里 2 条在跑」。

### 中栏：单条线的会话过程

- 消息不是平铺的，而是折叠成「步骤组」：`▼ 提交/保存 · keyframes ×6` → `已完成 5 个步骤 · 28 秒` → `思考了 8 秒` / `读取 inbox/douyin_7431.mp4` / `运行 ffmpeg ...`，工具调用保留完整命令和截断输出。
- 产物直接内联渲染（分镜缩略图 + 时间码 `00:02 / 00:09 / 00:21`），不用切窗口去看。
- 推断：**过程要细到命令级，结果要贴脸可看**。这是「可审计」而不是「可观赏」。

### 右栏：工作树 · 泳道

- 四条竖泳道并排，每条是一串事件节点：`链接已粘贴` → `交接 → Grok` → `交接 → Sol` → `topics.md` → `测试 3 失败` → `尝试 #1` → `等待 Codex 测试`。
- 节点带 commit 短哈希（`6e3779b`）、增删行数（`8.8k + 8.8k`）、状态图标。
- 底部图例给出 15 类轨迹事件：提交/保存、测试 ✗、产物、等待你、交接/无损、审查通过、分支、工具调用、外部线引用、检查点、模型切换、错误、合并、上下文压缩、重试。
- 跨泳道有一条弧线从 `keyframes ×6` 指向另一条泳道的 `topics.md`。
- 推断：右侧**不是日志流，是拓扑图**。弧线表示「这条线的产物被另一条线引用了」。人看这个面板的目的只有一个：**发现哪条线卡住了、卡在哪、要不要插手**。

### 顶部控制带

`Grok` / `Claude Opus` / `立即发射` / `继续`。模型名是任务线上可替换的执行者标签（`Grok+Opus`、`Sol`、`Codex`、`Kimi`、`你`），说明模型不是产品的主角，**任务线才是**。

### 一句话结论

这个产品的内核是三件事：**并行**（多条线同时跑）、**可观测**（事件级轨迹，不是聊天记录）、**可接管**（人作为一等公民随时插话、放行、换模型）。

## 二、目标用户

| 角色 | 典型场景 | 真正关心 |
| --- | --- | --- |
| 技术负责人 | 一天要推进 4 个需求 + 2 个线上缺陷 | 全线态势、谁卡住了、要不要现在介入 |
| 业务开发 | 从 Jira 领活 → 开发 → 自测 → 提 PR | 少敲重复命令，别丢上下文 |
| 缺陷修复者 | 收到一个「偶现崩溃」的 bug | 先复现，再定位，别改出副作用 |
| 代码评审者 | 看同事（或 agent）交上来的改动 | 改动范围、改动依据、验证证据 |
| PM / Scrum Master | 站会前对进度 | Jira 上的状态是不是真的 |

MVP 只服务第一类到第三类。评审者和 PM 是「顺带被服务」，不做独立入口。

## 三、现状的问题

程序员今天用聊天式编码工具，卡在六个地方：

| 问题 | 具体表现 | 代价 |
| --- | --- | --- |
| 串行阻塞 | 一条会话跑到编译/测试就干等，人只能刷手机 | 一天有效推进量受限于最慢的那一步 |
| 上下文黑洞 | 跑了 40 分钟，回来看见一屏滚动文字，不知道改了哪几个文件 | 不敢信任，只能重跑 |
| 产物不可见 | 结果在磁盘上，要自己开编辑器确认 | 验证成本高于生成成本 |
| 交接失真 | 换模型、换会话、第二天回来，要重新讲一遍背景 | 前 20 分钟都在「复述需求」 |
| 与需求脱节 | 需求写在 Jira，实现写在本机，两边不对账 | 站会上答不出「这个单子做到哪了」 |
| 一次性大 diff | 结束时丢出 2000 行改动 | 评审退化成扫读，风险全压在人身上 |

第 5 条是这个项目区别于通用编码工具的地方，也是用户明确提出来的约束：**需求必须从 Jira 看板取**。

## 四、需求推导

把上面的观察，逐条转成功能。这是后面 PRD 功能清单的来源。

| 观察到的事实 | 推断的用户需求 | 对应功能 |
| --- | --- | --- |
| 每条任务有独立 worktree 路径 | 并行不能靠人切分支，要靠系统隔离 | 任务线 = worktree + 分支，调度器管并发 |
| 步骤可折叠、命令完整可见 | 我要能审计，而不是看它表演 | 事件溯源 + 可展开的轨迹视图 |
| 泳道带 diff 行数 | 我需要感知「改动多大」 | 每个节点聚合 diff 统计 |
| 跨泳道弧线 | 一条线的成果会被另一条消费 | 跨线产物引用，显式建模 |
| 图例里有「等待你」 | 人是在流程里的一个节点，不是外挂 | 人工门禁事件，阻塞并高亮 |
| 图例里有「交接/无损」 | 换执行者不该丢信息 | 结构化交接简报 |
| 图例里有「上下文压缩」 | 长任务必然爆上下文 | 压缩产出独立事件与摘要产物 |
| 图例里有「测试 ✗」「重试」「尝试 #1」 | 失败是常态，要能看见第几次 | 失败与重试是一等事件，带尝试序号 |
| 模型名可切换 | 不同任务适合不同模型 | 模型网关，per-lane 绑定，可中途切换 |

补充两条来自「修复缺陷」场景的推导：

- **缺陷必须先复现**。没有失败用例的修复无法证明有效。因此缺陷类任务线有一个强制阶段：先写出能红的测试，再改代码，再看到它变绿。这条流程不开放给 agent 自行跳过。
- **证据要回写 Jira**。修复类工单的价值一半在改动，一半在「可追溯的验证记录」。

## 五、与现有做法的差异

1. **需求源是 Jira 看板，不是一段粘贴的文字**。任务线的身份就是 issue key，状态双向流动。
2. **泳道图是主视图**。多数工具把并发藏在标签页里，这里把它画成并排的列，一眼看出谁在等。
3. **交接是结构化的，不是「把历史全塞给下一个模型」**。简报有固定 schema，可被校验、可被回放。
4. **人工门禁是事件**。审批不是弹窗，是轨迹上一个节点，可审计、可超时、可追溯是谁放行。

## 六、边界与非目标

MVP 明确不做：

- **不自动合并到主干**。最多开 PR，合并必须人点。
- **不做多仓库编排**。一条任务线绑一个仓库。
- **不做移动端**。
- **不做 IDE 插件**。先把 Web 工作台做对。
- **不做通用对话**。每条线都必须挂着 issue，防止退化成聊天工具。
- **不自建模型**。通过网关接第三方模型。

## 七、成功标准

| 指标 | 定义 | MVP 目标 |
| --- | --- | --- |
| 需求到 PR 的中位时长 | issue 进入「就绪」到 PR 打开 | 比人工基线低 40% |
| 首次评审通过率 | PR 未被要求大改 | ≥ 50% |
| 人工介入次数 / 任务 | 包括放行、纠偏、补指令 | ≤ 3 |
| 轨迹完整率 | 有测试证据的 PR 占比 | ≥ 90% |
| 单位任务成本 | 模型 token + 沙箱时长 | 可解释、可按任务归因 |
| Jira 状态回写延迟 | 事件发生到 Jira 可见 | < 30 秒 |
| 交接后无效步骤占比 | 新执行者重复已完成工作 | < 10% |

最后一条是这套设计能不能立住的关键：如果交接之后新模型还在原地打转，并行和换模型就都成了表演。
