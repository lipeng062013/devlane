## 1. 产品定位

面向研发团队的 **AI 并行开发工作台**。把 Jira 看板上的一批 issue 变成多条可并行推进的任务线，每条线在一个隔离的 git worktree 里由 AI 执行者干活，全程产生可审计的事件轨迹，关键节点强制人工放行，最后产出 PR 并回写 Jira。

一句话：**看板进，PR 出，中间每一步都看得见。**

---

## 2. 核心概念与对象模型

| 对象 | 定义 | 关键属性 |
| --- | --- | --- |
| Project（空间） | 一个仓库 + 一套 Jira 连接的绑定 | 仓库地址、默认分支、Jira 站点、字段映射 |
| Issue 快照 | 从 Jira 拉取的 issue 不可变副本 | key、类型、摘要、描述（ADF）、验收标准、标签、优先级、报告人 |
| Lane（任务线） | 一条执行单元，1:1 绑定 issue（MVP 内） | 状态、worktree 路径、分支、执行者、成本 |
| Run（执行轮次） | lane 内一次连续执行 | 模型、开始/结束、token、尝试序号 |
| Event（事件） | 轨迹的最小单位，只追加 | 类型、actor、时间、payload、父事件 |
| Artifact（产物） | 事件产出的文件、补丁、测试报告、截图 | 路径、sha256、大小、类型 |
| Gate（门禁） | 需要人处理的中断点 | 类型、负责人、超时策略 |
| Brief（交接简报） | 交给下一个执行者的结构化上下文 | 固定 schema，见 §6.4 |
| Link（关联） | lane 与 issue、lane 与 lane、lane 与 PR | 类型、方向 |

关键约束：**Event 不可修改、不可删除**。任何「更正」都是新事件。UI 上呈现的一切（会话视图、泳道图、统计）都是事件流的投影。

## 3. 用户故事

按优先级排序，每条都写清验收口径。

**US-01 从看板取活（P0）**
作为开发，我想在平台上选择 Jira 看板和 Sprint，把待办 issue 一键拉成本地任务线。
验收：选择板 → 列出当前 Sprint 的 issue（含类型、优先级、状态、经办人）→ 勾选后可批量创建 lane → 每条 lane 自动建分支 `devlane/{issue-key}` 和 worktree。

**US-02 就绪检查（P0）**
作为技术负责人，我想在派活之前知道哪些 issue 信息不全。
验收：对每条 issue 计算就绪分，缺验收标准 / 缺复现步骤 / 缺关联设计 的给出具体缺项，并提供「直接派发」与「先补信息」两个动作。

**US-03 并行推进（P0）**
作为开发，我想同时推进多条线，互不踩脚。
验收：可配置并发上限（默认 4）；超限的任务排队并显示队列位置；不同 lane 的分支与 worktree 完全隔离。

**US-04 过程可审计（P0）**
作为评审者，我想看到每一步做了什么、依据是什么。
验收：轨迹按步骤组折叠，可展开到单条命令与截断输出；每个写文件操作关联到 diff；节点显示 commit 短哈希与增删行数。

**US-05 随时接管（P0）**
作为用户，我想在 AI 跑偏时立刻插话或暂停。
验收：任意时刻可暂停、可追加指令、可改执行者；接管动作本身记为事件并在图上可见。

**US-06 交接不丢信息（P0）**
作为用户，我想把一个跑到一半的线交给另一个模型继续。
验收：交接产生 Brief 产物；新执行者的首条消息必须声明「已读 Brief、计划下一步」；Brief 覆盖目标、验收标准、已完成、待办、关键决策、产物、未决问题。

**US-07 缺陷先复现（P0）**
作为修 bug 的人，我想确保修复真的修好了。
验收：缺陷类 issue 的 lane 在「写失败测试」阶段产出红色测试证据（命令 + 输出 + 退出码）之前，不允许进入修改阶段。

**US-08 门禁放行（P0）**
作为负责人，我想在合并前逐条确认。
验收：门禁卡片列出改动摘要、测试结果、风险点、Jira 回写内容；放行 / 打回 / 转人工 三个动作；超时可配置提醒与自动降级策略。

**US-09 回写 Jira（P0）**
作为 PM，我想在 Jira 上看到真实进度。
验收：状态流转、评论（含 PR 链接与验证摘要）、工时或成本字段按配置回写；失败时进入重试队列，不阻塞主线。

**US-10 成本与统计（P1）**
作为负责人，我想知道钱花在哪。
验收：按 lane、按模型、按天统计 token 与沙箱时长；单 lane 超预算可预警与中断。

**US-11 模板化（P1）**
作为团队，我们想固化自己的开发流程。
验收：可为 issue 类型绑定流水线模板（阶段、门禁、允许的工具集、测试命令）。

**US-12 知识沉淀（P2）**
把成功 lane 的 Brief 与轨迹收进项目知识库，供后续任务检索。

## 4. 功能需求

### 4.1 Jira 接入

| 功能 | 优先级 | 说明 |
| --- | --- | --- |
| OAuth 3LO 授权 | P0 | Cloud 站点，申请 `read:jira-work`、`write:jira-work`、`offline_access` |
| API Token 授权 | P0 | Data Center / 自建实例，Basic Auth |
| 站点与项目绑定 | P0 | 一个 Project 绑定一个 Jira 站点 + 一个或多个项目键 |
| 看板 / Sprint 浏览 | P0 | 通过 Agile API 取板、Sprint、Backlog |
| 批量导入 | P0 | 支持按 Sprint、按 JQL、按标签导入 |
| 字段映射配置 | P0 | 故事点、验收标准、环境、优先级等字段的 site-specific ID 映射 |
| 增量同步 | P0 | Webhook 优先，定时轮询兜底；变更写入 issue 快照 |
| 状态回写 | P0 | 按阶段与事件的映射表驱动，如「PR 打开」→「待评审」 |
| 评论回写 | P0 | ADF 格式，附 PR 链接、测试摘要、成本 |
| 字段回写 | P1 | 自定义字段（分支名、PR 号） |
| 双向冲突处理 | P1 | Jira 侧被人改动时提示，不静默覆盖 |

**明确不做**：Jira 服务管理（JSM）工单流、Confluence 同步、Jira 计划（高级路线图）。

### 4.2 任务线

**状态机**

```
draft → ready → queued → running ⇄ blocked
                   ↑          ↓
                paused ← 等待你
                              ↓
                          reviewing → merged
                              ↓
                          abandoned
```

| 状态 | 含义 | 谁能进入下一态 |
| --- | --- | --- |
| draft | 已导入，未校验 | 系统（自动做就绪检查） |
| ready | 信息齐全，可派发 | 人（点派发）或自动策略 |
| queued | 等并发额度 | 调度器 |
| running | 执行中 | 执行者 |
| blocked | 遇到门禁或依赖 | 事件驱动 |
| paused | 人主动暂停 | 人 |
| reviewing | 已开 PR | 人 / CI |
| merged | 已合并 | 人 |
| abandoned | 放弃 | 人 |

规则：
- `queued` 超过 30 分钟未启动，界面标黄并提示调整并发。
- `blocked` 必须携带门禁 ID，不允许匿名阻塞。
- 任一 lane 状态变化同步触发事件与（可选的）Jira 回写。

**就绪检查评分**

| 检查项 | 权重 | 缺失后果 |
| --- | --- | --- |
| 有验收标准（或可从描述解析出 Given/When/Then） | 30 | 无法判断完成 |
| 缺陷类有复现步骤与期望/实际 | 30 | 无法写失败测试 |
| 有明确影响范围（模块、文件、接口） | 20 | 探索成本翻倍 |
| 有优先级与截止时间 | 10 | 排不进队列 |
| 有报告人或负责人 | 10 | 无人可问 |

< 70 分进入「先补信息」，提供一键在 Jira 评论追问的模板。

### 4.3 执行与隔离

- 每条 lane 一个 worktree：`{repo}/.devlane/worktrees/{issue-key}`，分支 `devlane/{issue-key}`。
- 每个 Run 在容器沙箱内执行：非 root、只挂载该 worktree、网络默认出站白名单（包仓库、模型网关、Jira），禁止访问内网其它服务。
- 资源上限：CPU 2 核、内存 4 GB、磁盘 10 GB、单 Run 时长上限（默认 45 分钟）。
- 命令白名单 + 危险命令拦截（`rm -rf /`、`git push --force`、修改远端、读取 `~/.ssh` 等）。
- 所有写操作先落补丁，再由平台应用，保留可回滚点（每个 save 事件即一个检查点）。

### 4.4 双视图

**会话视图（中栏）**

- 步骤组折叠：组标题显示动作摘要 + 步数 + 耗时。
- 工具调用内联卡片：命令、退出码、输出（超长截断，可展开）。
- 产物内联：diff、图片、测试报告、Markdown。
- 输入区支持：继续对话、引用文件（`@`）、引用 issue 字段、切换执行者。

**泳道视图（右栏）**

- 一行一 lane，横向滚动；节点按事件类型着色，图例固定。
- 节点信息密度：类型图标 + 一行摘要 + 可选 commit 短哈希 + diff 统计。
- 悬停显示事件详情浮层；点击定位到会话视图对应位置（双向跳转是硬要求）。
- 跨 lane 引用画弧线，可点击查看沿用的具体产物。
- 顶部有全局筛选：只看阻塞、只看失败、只看需要我。

### 4.5 人工门禁

| 门禁类型 | 触发点 | 默认动作 |
| --- | --- | --- |
| 计划确认 | 首个执行者的实现计划产出后 | 放行 / 修改要求 |
| 范围变更 | 需要触碰 lane 声明范围外的文件 | 放行 / 缩小范围 |
| 高风险操作 | 改依赖、改数据库迁移、改鉴权、改支付 | 必须人工确认 |
| PR 放行 | 测试通过且 diff 就绪 | 开 PR / 打回 |
| 预算超限 | 超过单 lane 预算 80% | 继续 / 中断 |
| 信息缺失 | 就绪分不足且人选择强推 | 记录风险后继续 |

门禁统一以「等待你」节点呈现，带倒计时。超时策略三选一：提醒、自动暂停、按默认动作放行（高风险门禁不允许自动放行）。

### 4.6 交接

触发条件：手动切换执行者、上下文压缩后重建、人工接管结束、Run 失败重试。

Brief schema（固定字段，缺项拒绝交接）：

```
goal            目标一句话
acceptance      验收标准（列表）
plan            当前计划与所处阶段
done            已完成事项（含证据链接）
todo            待办事项
decisions       关键决策与理由
artifacts       产物清单（路径 + sha256 + 一句话说明）
open_questions  未决问题
repo_state      分支、HEAD、未提交改动、最近 5 个 commit
next_step       建议的第一步
```

校验：新执行者的首个事件必须是 `brief_ack`，声称已读并给出下一步。若首 3 个事件与 `done` 重复，标记「交接退化」并在图上提示。

### 4.7 缺陷修复专用流水线

```
复现 → 失败测试（红） → 定位 → 最小修复 → 测试全绿 → 回归范围核对 → PR
```

硬约束：
- 无红色测试证据不得进入「定位」及之后阶段。
- 修复后必须重跑该测试文件 + 受影响模块的测试集。
- PR 描述必须包含：根因、改动点、验证方式、影响面、回滚方式。

### 4.8 验证与交付

- 每类改动有对应验证命令（由项目配置：单测、lint、类型检查、构建、E2E）。
- 验证结果以事件记录，包含命令、退出码、耗时、摘要输出。
- 失败自动重试上限 3 次，每次生成新尝试序号，超过则转门禁。
- 交付物：PR（标题含 issue key、正文按模板、关联 Jira）、Jira 评论、成本报告。

### 4.9 观测与成本

- 实时：在线 lane 数、队列深度、平均等待、门禁滞留时长、失败率。
- 成本：按 lane / 模型 / 天聚合 token 与沙箱时长；单 lane 预算告警。
- 审计：任意事件的 actor、时间、依据可查；导出为 JSONL 供归档。

## 5. 非功能需求

| 类别 | 要求 |
| --- | --- |
| 性能 | 泳道视图 2000 事件内首屏 < 1.5s；事件流式推送延迟 < 1s |
| 一致性 | 事件只追加；投影可重放；断线重连后按 seq 补拉，不丢不重 |
| 可靠性 | 单 lane 崩溃不影响其它 lane；调度器重启后可恢复 running 状态 |
| 安全 | Jira token 加密存储；沙箱默认拒绝出站；仓库凭据按需注入、用后销毁 |
| 提示注入防护 | issue 正文视为不可信输入，工具调用受 lane 策略约束，越权即阻塞 |
| 可观测 | 全链路 trace id；模型调用记录请求摘要、耗时、token |
| 合规 | 轨迹与产物保留期可配（默认 90 天）；支持整 lane 导出与删除 |
| 国际化 | 界面中英双语；Jira 内容原样保留 |

## 6. 交互要点

1. **默认落点是看板**，不是聊天框。用户先看见「有哪些活」，再决定派谁干。
2. **三条线的信息必须能在一屏内比较**：每条 lane 顶部固定显示阶段、执行者、已耗时、阻塞原因。
3. **中断要显眼**：需要人的 lane 在左栏、右栏、顶部计数三处同时提示，且排序置顶。
4. **失败不隐藏**：`测试 ✗` 保留在图上，不因重试成功而消失。
5. **写操作可回滚**：任一检查点可「回退到此」，生成新分支而非强推。

## 8. 发布计划

| 阶段 | 范围 | 出口标准 |
| --- | --- | --- |
| M0（3 周） | Jira 只读接入、issue 导入、就绪检查、单 lane 手动执行、会话视图 | 能把一个真实 issue 跑成一次 commit |
| M1（4 周） | 并行调度、worktree 隔离、泳道视图、门禁、交接 Brief | 4 条 lane 并行不互相干扰 |
| M2（3 周） | 缺陷流水线、验证命令、PR 创建、Jira 回写 | 端到端闭环，缺陷类有红绿证据 |
| M3（2 周） | 成本统计、模板、审计导出 | 可对内推广到 2 个团队 |

## 9. 风险

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| Jira 字段因站点而异 | 导入失败或丢信息 | 字段映射配置化 + 自动探测 + 校验预览 |
| 状态流转 ID 各工作流不同 | 回写报错 | 按名称解析 transition，缓存并失败回退到「加评论」 |
| Jira 正文含提示注入 | agent 执行越权操作 | 正文与指令分区、工具白名单、越权即阻塞 |
| 并行导致评审压力集中 | PR 堆积 | 单项目并发上限 + PR 队列视图 |
| 交接质量不稳定 | 重复劳动、成本上升 | Brief schema 强校验 + 退化检测 |
| 缺陷修复改出副作用 | 线上事故 | 强制红绿证据 + 影响面核对 + 不允许自动合并 |

## 10. 验收清单（MVP）

- [ ] 能从 Jira 看板选 Sprint 并批量导入 10 个 issue
- [ ] 就绪检查能指出具体缺项，并生成追问评论草稿
- [ ] 4 条 lane 并行执行，worktree 与分支互不干扰
- [ ] 泳道图能看清「谁在等、等什么」，点击可跳到对应会话位置
- [ ] 任一时刻可暂停并追加指令，动作在图上可见
- [ ] 换执行者后 Brief 完整，新执行者不重复已完成工作
- [ ] 缺陷 lane 在无红色测试时无法进入修复阶段
- [ ] 门禁放行后能创建 PR，PR 正文符合模板
- [ ] Jira 状态与评论在 30 秒内可见
- [ ] 输出一份按 lane 归因的成本报告
